# 3. Shared Coding Standards

Every implementation shall follow:

* SOLID
* DRY
* KISS
* YAGNI
* PSR-12

Additional standards:

* Strict typing
* Constructor property promotion
* Native PHP Enums
* Readonly properties where appropriate
* Final classes unless inheritance is intentional
* Small, focused classes
* Single responsibility methods

| Job        | `SendPushNotificationJob`     |
| Enum       | `SubscriptionStatusEnum`      |
| Exception  | `PurchaseFailedException`     |

---

## Methods

Use verb-first naming.

Examples:

```text
createSubscription()
calculateRadar()
issueToken()
scheduleReminder()
completePurchase()
```

Avoid ambiguous names such as `handleData()` or `process()`.

---

# 7. DTO Standards

Rules:

* Immutable.
* Strongly typed.
* No framework dependencies.
* No validation logic.
* No persistence logic.

DTOs define service boundaries and are the only objects passed into services from controllers.

---

# 8. API Resource Standards

Resources are responsible for:

* Response transformation.
* Attribute formatting.
* Conditional relationships.
* API version stability.

Resources never execute business logic.

---

# 9. Exception Hierarchy

Suggested hierarchy:

```text
ApplicationException
│
├── ValidationException
├── AuthenticationException
├── AuthorizationException
├── DomainException
│   ├── SubscriptionException
│   ├── PurchaseException
│   └── RadarException
├── IntegrationException
└── InfrastructureException
```

All exceptions are converted into the standard API response envelope.

# 10. Logging Standards

Every log entry should include:

* Timestamp
* Severity
* Correlation ID
* User ID (when available)
* Domain
* Action
* Context

Sensitive data (passwords, tokens, secrets, payment credentials) must never be logged.

# 15. Dependency Injection Rules

Dependencies are injected through constructors.

Allowed:

```php
public function __construct(
    private readonly SubscriptionRepositoryInterface $repository
) {}
```

Not allowed:

* Service location.
* Static access to business services.
* Manual instantiation of domain services inside controllers.

---

# 16. Event Standards

Rules:

* Events describe completed facts.
* Listeners perform one responsibility.
* Jobs execute asynchronously.
* Events dispatched after database commit.
* Long-running work belongs in queues.

---

# 17. Transaction Standards

Use database transactions when:

* Multiple tables are modified.
* External effects depend on successful persistence.
* Business invariants span multiple repositories.

Keep transactions as short as possible.

# 21. Implementation Guardrails

Mandatory rules:

* No business logic in controllers.
* No validation in controllers.
* No raw arrays passed to services.
* No direct model responses.
* No hardcoded configuration.
* No bypassing repositories.
* No synchronous execution of long-running tasks.
* No framework-specific code in DTOs.
* No direct vendor SDK usage inside domains.

## Recommended Enhancements (Adopted)

Based on everything we've established, I recommend formally adding these items to the implementation plan:

1. **Outbox Pattern** for reliable domain event publishing.
2. **Correlation ID Middleware** for end-to-end request tracing.
3. **Optimistic Concurrency Control** for mutable business records.
4. **Feature Flags** backed by configuration/database for safe rollout of future modules (Wallet, Loans, Insurance, AI Assistant).
5. **Provider Adapter Layer** using the Strategy + Adapter patterns so airtime/data providers can be added without modifying domain services.
6. **Domain Service Contracts** for all external integrations, ensuring the core domain remains vendor-agnostic.

These additions fit naturally within the architecture and strengthen long-term maintainability.

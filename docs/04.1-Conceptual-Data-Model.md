# Overview
We are now designing the **business semantics** of the platform—not tables, columns, or foreign keys. This document defines *what the business manages* and *how those concepts relate*, independent of any database implementation.

This conceptual model becomes the foundation for the logical model, ER diagram, migrations, repositories, services, and APIs.

# 1. Purpose

This document defines the business-level conceptual data model for YouStayOn.

It identifies:

* Bounded contexts
* Aggregate roots
* Business entities
* Ownership rules
* Domain relationships
* Future expansion domains

This model intentionally avoids:

* Physical tables
* SQL data types
* Primary keys
* Foreign keys
* Indexes

Those are introduced in later parts of Milestone 01.4.

---

# 2. Conceptual Modeling Principles

The conceptual model follows Domain-Driven Design (DDD).

Principles:

* Every business concept belongs to one bounded context.
* Every aggregate has one aggregate root.
* Ownership is explicit.
* Cross-domain communication occurs through services and events.
* Concepts are modeled independently of persistence.

---

# 3. Bounded Contexts

The platform is divided into the following bounded contexts.

| Context                   | Responsibility                               | Aggregate Root           |
| ------------------------- | -------------------------------------------- | ------------------------ |
| Identity & Access         | User identity, authentication, authorization | User                     |
| Subscription Management   | Utility subscriptions                        | Subscription             |
| Usage Intelligence        | Data usage and predictions                   | Radar Analysis           |
| Purchase                  | Airtime, data and future utility purchases   | Purchase                 |
| Notification              | Reminder and notification lifecycle          | Notification             |
| Dashboard                 | User summaries and analytics                 | Dashboard Snapshot       |
| Security                  | Audit, device activity and security events   | Security Activity        |
| Administration            | Platform administration and configuration    | Administration           |
| Configuration             | Dynamic business configuration               | Configuration            |
| Future Financial Services | Wallet, savings, loans, investments          | Wallet (future)          |
| AI Services               | AI assistant and recommendations             | AI Conversation (future) |

# 4. Aggregate Roots

Aggregate roots enforce consistency within their boundaries.

| Aggregate                | Description                               |
| ------------------------ | ----------------------------------------- |
| User                     | Represents a platform account             |
| Subscription             | Represents an active utility subscription |
| Purchase                 | Represents a purchase transaction         |
| Notification             | Represents a notification lifecycle       |
| Radar Analysis           | Represents calculated usage intelligence  |
| Dashboard Snapshot       | Represents aggregated dashboard data      |
| Security Activity        | Represents security-related events        |
| Configuration            | Represents configurable business settings |
| Wallet (Future)          | Represents a financial wallet             |
| AI Conversation (Future) | Represents AI interaction history         |

Only aggregate roots are referenced directly by other aggregates.

# 6. Ownership Rules

Ownership follows aggregate boundaries.

Examples:

* A User owns Subscriptions.
* A Subscription owns Usage Records.
* A Subscription owns Reminder Rules.
* A Purchase owns Provider Responses.
* A Notification owns Delivery Attempts.
* A Radar Analysis owns Recommendations.

Child entities cannot exist independently of their aggregate root unless explicitly modeled as separate aggregates.

# 12. Conceptual Integrity Rules

The following business rules apply:

* Every Subscription belongs to exactly one User.
* Every Purchase is initiated by exactly one User.
* Every Notification targets exactly one User.
* Every Radar Analysis is generated from one Subscription.
* Dashboard information is derived, not authoritative.
* Audit records are immutable.
* Configuration is shared, not duplicated across domains.

---

# 13. Business Invariants

Key invariants include:

* A Subscription cannot exist without an owning User.
* A Reminder cannot exist without a Subscription.
* A Usage Record must belong to a Subscription.
* A Purchase cannot exist without a User.
* A Radar Analysis requires historical usage data.
* Audit events are never modified after creation.

These invariants will be enforced in the domain and persistence layers.

## Architectural Decisions Confirmed

The following decisions are now fixed for subsequent database design:

* Bounded contexts map directly to backend domains.
* Aggregate roots define transactional consistency boundaries.
* Cross-context interactions use services and domain events.
* Shared reference concepts will become centralized lookup/configuration structures.
* Future fintech and AI modules will extend the model through new bounded contexts rather than modifying existing aggregates.

### Database architecture recommendation

Before we start the logical model, I recommend adopting two additional conventions that will improve long-term maintainability:

1. **Surrogate primary keys** (`BIGINT UNSIGNED` auto-increment for MVP, with the option to migrate to UUID/ULID externally later if needed). This keeps joins efficient and simplifies provider integrations.
2. **Universally available audit columns** as a conceptual standard: every mutable aggregate should conceptually support `created_by`, `updated_by`, and, where appropriate, `deleted_by` in addition to timestamps. Even if some are introduced later, designing for them now avoids disruptive schema evolution.

# Backend Architecture

**Project:** YouStayOn

**Version:** 1.0

**Architecture:** Modular Domain-Driven Monolith

**Framework:** Laravel 12

**Language:** PHP 8.3+

---

# 1. Purpose

This document defines the definitive backend architecture for YouStayOn.

It establishes:

* Domain boundaries
* Layer responsibilities
* Dependency rules
* Data flow
* Folder organization
* Coding patterns
* Cross-cutting infrastructure

Every backend implementation from Milestone 02 onward shall conform to this architecture.

---

# 2. Architectural Style

The backend is implemented as a **Modular Domain-Driven Monolith**.

Characteristics:

* Single deployable Laravel application.
* Independent business domains.
* Shared infrastructure.
* Explicit contracts between layers.
* No direct coupling between domains.
* Future-ready for service extraction.

Each domain encapsulates its own business logic and exposes behavior through services and contracts rather than direct model access.

---

# 3. Dependency Rule

Dependencies shall always point inward.

```text
HTTP Layer
      │
      ▼
Application Layer
      │
      ▼
Domain Layer
      │
      ▼
Infrastructure Layer
```

Forbidden dependencies include:

* Controllers accessing models directly.
* Controllers performing business logic.
* Services querying the database without repositories.
* Widgets or clients depending on persistence details.

---

```text

        │
```

```text
        │
```

# 7. Core Layer

The Core layer contains reusable infrastructure that is independent of any business domain.

Examples:

```text
Core/
├── Contracts/
├── DTOs/
├── Enums/
├── Exceptions/
├── Helpers/
├── Providers/
├── Repositories/
├── Services/
├── Support/
├── Traits/
└── ValueObjects/
```

Responsibilities:

* Base abstractions
* Shared interfaces
* Common services
* Infrastructure helpers
* Generic exceptions
* Shared value objects

The Core layer must not contain business rules specific to subscriptions, purchases, or users.

---

# 8. Shared Layer

The Shared layer contains reusable functionality that multiple domains depend upon but that is still business-oriented.

Examples:

* Audit logging
* Notification abstractions
* API response builders
* Pagination utilities
* Common validation rules
* Shared middleware

Unlike Core, Shared may contain business-aware concepts that span multiple domains.

---

# 9. Domain Structure

Each domain is autonomous.

Example:

```text
Domains/
└── Subscription/
    ├── Contracts/
    ├── Controllers/
    ├── DTOs/
    ├── Enums/
    ├── Events/
    ├── Listeners/
    ├── Models/
    ├── Policies/
    ├── Repositories/
    ├── Requests/
    ├── Resources/
    ├── Services/
    └── Tests/
```

A domain owns its models, services, repositories, and business rules.

---

# 10. Domain Responsibilities

| Domain       | Responsibility                                        |
| ------------ | ----------------------------------------------------- |
| Auth         | Authentication, OTP, session lifecycle                |
| User         | Profile, preferences, account management              |
| Dashboard    | Aggregated user dashboard                             |
| Subscription | Utility subscriptions and renewals                    |
| Purchase     | Airtime, data, cable, internet, electricity purchases |
| Radar        | Usage analytics and predictive intelligence           |
| Notification | Push and in-app notifications                         |
| Security     | Devices, audit logs, login history                    |
| Admin        | Platform administration and configuration             |

---

# 11. Cross-Domain Communication

Domains must not access each other's repositories directly.

Preferred communication:

* Service contracts
* Domain events
* Shared abstractions

This prevents tight coupling.

---

# 12. Repository Pattern

Every aggregate has:

```text
Repository Interface
        │
        ▼
Repository Implementation
```

Example:

```text
SubscriptionRepositoryInterface
        │
        ▼
SubscriptionRepository
```

Repositories are responsible only for data access.

Business decisions remain in services.

---

# 13. Service Layer

Services orchestrate business use cases.

Responsibilities:

* Validate business rules
* Coordinate repositories
* Manage transactions
* Dispatch events
* Invoke external integrations
* Return domain results

Services must remain stateless.

---

# 14. DTO Strategy

All business operations use immutable DTOs.

Examples:

* RegisterUserDTO
* LoginDTO
* CreateSubscriptionDTO
* PurchaseDataDTO
* DashboardSummaryDTO

Arrays shall not be passed through service boundaries.

---

# 15. Event-Driven Design

Important business actions emit domain events.

Examples:

```text
UserRegistered
SubscriptionCreated
PurchaseCompleted
ReminderTriggered
RadarCalculated
```

Listeners perform secondary work such as notifications, audit logging, or analytics.

---

# 16. Transaction Management

Database transactions are required for operations involving multiple writes.

Examples:

* Registration
* Purchases
* Subscription creation
* Profile updates affecting multiple tables

Services are responsible for transaction boundaries.

---

# 17. Error Handling

Errors shall propagate through centralized exception handling.

Custom exception hierarchy:

```text
BusinessException
ValidationException
AuthenticationException
AuthorizationException
ProviderException
PurchaseException
RadarException
```

API responses shall always use the standardized response envelope.

---

# 18. Configuration Management

Runtime configuration belongs in:

* Environment variables
* Configuration files
* Database tables

Never hardcode:

* Provider names
* Thresholds
* URLs
* API keys
* Reminder intervals
* Limits

---

# 19. Architectural Constraints

Mandatory rules:

* Thin controllers
* Thin models
* No business logic in repositories
* No business logic in middleware
* No direct model responses
* No static service access
* Constructor dependency injection only
* Explicit interfaces for repositories
* DTOs for all business operations
* API Resources for all responses

---

# 20. Evolution Strategy

The architecture is intentionally modular.

If future scale demands it, domains such as Purchase or Notification can be extracted into independent services with minimal disruption because dependencies already flow through contracts and events.

### One architectural note

As we continue, I'll also ensure that the backend and Flutter architectures **mirror each other** wherever practical. For example, if the backend has a `Subscription` domain, Flutter will have a corresponding `subscription` feature with aligned use cases and models. This symmetry reduces cognitive load, makes onboarding easier, and simplifies tracing a feature from UI to API to database. It's a pattern commonly used in larger production systems and fits well with the long-term vision for YouStayOn.

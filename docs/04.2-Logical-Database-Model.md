**Milestone 01.4 Part 02** is where the business model becomes a **database model**, while still remaining database-platform independent.

Unlike the conceptual model (which describes *business concepts*), the logical model defines:

* Logical entities
* Relationships
* Cardinality
* Aggregate ownership
* Associative entities (junctions)
* Candidate keys (conceptually)
* Lifecycle dependencies

It still intentionally excludes SQL-specific concerns such as data types, indexes, storage engines, and migration order.

# 1. Purpose

This document transforms the conceptual business model into a logical database model suitable for conversion into a physical Entity Relationship Diagram (ERD).

It defines:

* Logical entities
* Relationship cardinality
* Aggregate ownership
* Associative entities
* Inheritance strategy
* Domain ownership
* Lifecycle dependencies

It intentionally excludes:

* SQL data types
* Storage engines
* Index definitions
* Physical constraints
* Migration implementation

---

# 2. Logical Design Principles

The logical model follows these principles:

* Every aggregate root maps to a primary logical entity.
* Child entities exist within the lifecycle of their owning aggregate unless explicitly promoted to an aggregate.
* Many-to-many relationships are resolved through associative entities.
* Shared reference data is centralized.
* Derived data is modeled separately from transactional data.

# 6. Many-to-Many Relationships

The following conceptual N:M relationships are resolved using associative entities.

| Relationship                             | Associative Entity      |
| ---------------------------------------- | ----------------------- |
| User ↔ Role                              | User Role               |
| Role ↔ Permission                        | Role Permission         |
| Feature Flag ↔ Environment (future)      | Feature Flag Assignment |
| Referral Campaign ↔ Reward Rule (future) | Campaign Reward Rule    |

This avoids implicit many-to-many relationships in the physical model.

# 8. Lifecycle Dependencies

Lifecycle rules define creation and deletion dependencies.

| Parent         | Child            | Dependency |
| -------------- | ---------------- | ---------- |
| User           | User Profile     | Required   |
| User           | Subscription     | Required   |
| Subscription   | Usage Record     | Required   |
| Subscription   | Reminder         | Required   |
| Purchase       | Purchase Item    | Required   |
| Notification   | Delivery Attempt | Required   |
| Radar Analysis | Recommendation   | Required   |

Dependent entities cannot outlive their parent aggregate unless explicitly archived.

---

# 9. Inheritance Strategy

The logical model favors composition over inheritance.

Where variation exists (for example, purchase providers or notification channels), behavior is modeled through:

* Configuration
* Strategy pattern
* Reference entities
* Enums

No table-per-class or table-per-hierarchy inheritance is planned.

# 14. Logical Integrity Rules

The following rules govern the logical model:

* Every Subscription references one User.
* Every Purchase references one User.
* Every Radar Analysis references one Subscription.
* Every Recommendation belongs to one Radar Analysis.
* Every Notification belongs to one User.
* Every Delivery Attempt belongs to one Notification.
* Every Usage Record belongs to one Subscription.
* Every Purchase Item belongs to one Purchase.

These rules will become foreign key constraints in the physical model.

### Architectural recommendation

Before the physical schema, I recommend one refinement to the logical model: introduce a **Provider Capability** reference entity (e.g., supports airtime, data, cable, electricity, bill inquiry). Instead of embedding service capabilities into provider-specific logic, the application can determine available features dynamically. This aligns with our "no hardcoding" rule and makes onboarding new providers substantially easier.

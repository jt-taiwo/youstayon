# Flutter Architecture

**Project:** YouStayOn

**Version:** 1.0

**Architecture:** Feature-First Clean Architecture

**Framework:** Flutter (Material 3)

**Language:** Dart

---

# 1. Purpose

This document defines the definitive Flutter architecture for YouStayOn.

It establishes:

* Project structure
* Layer responsibilities
* Feature organization
* State management
* Navigation
* Dependency injection
* API communication
* Secure storage
* Offline support
* Design system
* Testing strategy

Every Flutter implementation shall conform to this document.

---

# 2. Architectural Goals

The Flutter application shall be:

* Maintainable
* Scalable
* Testable
* Modular
* Performant
* Secure
* Offline-capable (where practical)
* Consistent with the backend architecture

Business logic shall never reside inside widgets.

---

# 3. Architectural Style

The application follows **Feature-First Clean Architecture**.

Each feature owns:

* UI
* Business logic
* Use cases
* Repository contracts
* Data sources
* Models

Cross-cutting functionality lives in `core`.

---

# 4. Dependency Rule

Dependencies always point inward.

```text
UI (Widgets)
        │
        ▼
BLoC / Cubit
        │
        ▼
Use Cases
        │
        ▼
Repository Interface
        │
        ▼
Repository Implementation
        │
        ▼
Remote / Local Data Source
        │
        ▼
REST API / Secure Storage / Cache
```

Forbidden dependencies include:

* Widgets calling Dio directly.
* Widgets containing business rules.
* UI importing remote data sources.
* BLoCs depending on concrete repository implementations.

Responsible for application bootstrap.

```text
app/
├── app.dart
├── router.dart
├── routes.dart
├── theme.dart
├── bootstrap.dart
└── dependency_injection.dart
```

Responsibilities:

* App initialization
* Dependency injection bootstrap
* Global routing
* Theme registration
* Error handling
* Environment configuration

---

# 7. core/

Contains framework-independent shared infrastructure.

```text
core/
├── api/
├── cache/
├── config/
├── constants/
├── design_system/
├── errors/
├── network/
├── services/
├── storage/
├── theme/
├── utils/
└── widgets/
```

Examples:

* Dio configuration
* API client
* Theme
* Secure storage
* Connectivity service
* Shared dialogs
* Common buttons
* Common cards
* Error handling

The `core` package must not depend on any business feature.

---

# 8. shared/

Reusable business-aware components.

Examples:

* Notification badge
* Utility cards
* Transaction tiles
* Provider logos
* Dashboard summaries
* Avatar widgets

Unlike `core`, `shared` may understand application concepts but not own business rules.

# 11. Layer Responsibilities

## Presentation

Contains:

* Screens
* Widgets
* BLoCs
* Dialogs
* Bottom sheets
* Navigation events

No business logic.

---

## Domain

Contains:

* Entities
* Use Cases
* Repository Interfaces

Pure Dart.

No Flutter dependency.

---

## Data

Contains:

* DTO models
* Repository implementations
* Remote data sources
* Local data sources
* JSON serialization

Responsible only for data retrieval and persistence.

---

# 12. State Management

Official state management:

**flutter_bloc**

Each feature owns its own BLoCs.

Example:

```text
AuthBloc
DashboardBloc
SubscriptionBloc
PurchaseBloc
RadarBloc
```

Rules:

* One responsibility per BLoC.
* Immutable states.
* Events represent user intent.
* Side effects delegated to use cases.

---

Navigation uses **GoRouter**.

Structure:

```text
/
├── splash
├── onboarding
├── login
├── register
├── otp
├── dashboard
├── subscriptions
├── purchases
├── radar
├── profile
├── security
└── settings
```

Protected routes require authentication.

---

# 14. Dependency Injection

Dependency injection shall be centralized.

Recommended package:

* `get_it`

Responsibilities:

* Repository registration
* API client
* Secure storage
* Use cases
* Services
* BLoCs

No manual dependency creation inside widgets.

---

# 15. API Communication

Official HTTP client:

**Dio**

Architecture:

```text
Widget
    │
Bloc
    │
Use Case
    │
Repository
    │
Remote Data Source
    │
Dio Client
    │
Laravel API
```

Features:

* Authentication interceptor
* Automatic token injection
* Request/response logging (development only)
* Error mapping
* Retry strategy (configurable)
* Timeout configuration

---

# 16. Authentication Flow

Authentication tokens shall be stored using:

**Flutter Secure Storage**

Never use:

* SharedPreferences
* Plain text files

The authentication flow:

```text
Login
   │
API
   │
Access Token
   │
Secure Storage
   │
Authenticated Requests
```

---

# 17. Offline Strategy

The MVP supports limited offline capability.

Cached:

* User profile
* Dashboard snapshot
* Subscription list
* Notification history
* Recently viewed data

When offline:

* Display cached data.
* Queue user actions where appropriate (future enhancement).
* Show connectivity status.

The architecture should allow future expansion to a more comprehensive offline-first model.

* NetworkFailure
* AuthenticationFailure

# 21. Performance Guidelines

The application shall:

* Avoid unnecessary rebuilds.
* Use `const` constructors where applicable.
* Use lazy loading.
* Paginate large lists.
* Cache images.
* Dispose controllers appropriately.
* Minimize widget tree depth.

* Unit tests for use cases.
* Repository tests.
* BLoC tests.
* Widget tests.
* Integration tests for critical flows.

### Architectural refinement for later implementation

When we reach the Flutter implementation milestone, I recommend adding a small `bootstrap` layer that initializes the application in a deterministic order:

1. Load environment configuration.
2. Initialize logging.
3. Initialize secure storage.
4. Register dependency injection.
5. Configure Dio.
6. Initialize Firebase (FCM).
7. Initialize local cache.
8. Build the router.
9. Launch the app.

This startup sequence keeps initialization predictable, simplifies testing, and cleanly separates application startup from UI construction. It fits naturally into the architecture we've defined and complements the backend bootstrap process.

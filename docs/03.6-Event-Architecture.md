# Overview
This document establishes the **asynchronous backbone** of YouStayOn. While Part 05 defined the synchronous request lifecycle, **Part 06** defines everything that happens *after* the database transaction commits. By adopting an event-driven architecture from the outset, we reduce coupling between domains, improve responsiveness, and prepare the platform for future scalability without changing business logic.

# 2. Architectural Principles

The event system follows these principles:

* Business events describe facts that have already occurred.
* Events are immutable.
* Events are dispatched only after successful business transactions.
* Event handlers are independent.
* Side effects occur asynchronously whenever practical.
* Event processing must be retry-safe.
* Event processing must be observable.
* Failed events must not compromise the originating transaction.

---

| Category           | Purpose                                   |

| Integration Events | Communication with external services      |

# 4. Event Processing Lifecycle

```text
User Action
      │
      ▼
Controller
      │
      ▼
Service
      │
Database Transaction
      │
Commit
      │
      ▼
Domain Event
      │
      ▼
Event Dispatcher
      │
      ▼
Listeners
      │
      ▼
Queued Jobs
      │
      ▼
External Services
```

Events are dispatched **only after** the originating transaction has been committed successfully.

---

# 5. Event Naming Convention

Events shall use **Past Tense** because they represent completed facts.

Examples:

```text
UserRegistered
UserLoggedIn
UserLoggedOut

SubscriptionCreated
SubscriptionUpdated
SubscriptionDeleted

PurchaseCompleted
PurchaseFailed

ReminderScheduled
ReminderTriggered

RadarCalculated

NotificationQueued
NotificationSent

AuditLogCreated
```

Avoid command-style names such as:

* CreateSubscription
* SendNotification
* ProcessPurchase

These are actions, not events.

---

# 6. Listener Naming Convention

Listeners describe reactions.

Examples:

```text
SendWelcomeNotification

ScheduleRenewalReminder

GenerateAuditLog

CalculateRadarStatistics

UpdateDashboardCache

NotifyAdministrators

RefreshUserDashboard
```

Each listener has one responsibility.

---

# 7. Job Naming Convention

Queued jobs represent executable background work.

Examples:

```text
SendPushNotificationJob

SendReminderJob

GenerateDashboardSnapshotJob

RefreshRadarStatisticsJob

CallProviderApiJob

GenerateReceiptJob

CleanupExpiredTokensJob
```

Jobs are implementation details—not business events.

# 9. Reminder Engine

The Reminder Engine is event-driven.

Example flow:

```text
SubscriptionCreated
        │
        ▼
ScheduleReminder Listener
        │
        ▼
Reminder Job
        │
        ▼
Queue
        │
        ▼
Scheduled Execution
        │
        ▼
ReminderTriggered
        │
        ▼
Push Notification
```

The engine never embeds reminder timing in code.

Reminder schedules are configurable.

# 14. Retry Strategy

Background jobs may fail.

Retry policy:

* Exponential backoff (configurable).
* Maximum retry attempts configured centrally.
* Permanent failures moved to the failed jobs store.
* Failures logged with correlation identifiers.

Retries should be reserved for transient failures such as network issues or temporary service outages.

---

# 15. Idempotency Rules

Every queued job shall be designed to avoid duplicate side effects.

Examples:

Safe:

* Recalculating dashboard summaries.
* Refreshing cached analytics.

Protected:

* Sending notifications.
* Recording purchases.
* Calling provider APIs.

Idempotency keys should be used where repeated execution could otherwise produce duplicate outcomes.

---

# 16. Event Ordering

Rules:

* Parent transaction completes first.
* Domain event dispatched after commit.
* Listeners execute independently.
* Jobs execute asynchronously.
* Failures in one listener do not block unrelated listeners.

Ordering between unrelated listeners should not be relied upon unless explicitly coordinated.

---

# 18. Correlation IDs

Every request receives a Correlation ID.

The identifier propagates through:

* HTTP request
* Domain events
* Queued jobs
* External integrations
* Logs
* Audit records

This enables end-to-end tracing across synchronous and asynchronous operations.

---

# 19. Observability

Every background process records:

* Start time
* Completion time
* Duration
* Retry count
* Queue name
* Correlation ID
* Success or failure

Metrics should be suitable for future dashboards and alerting.

---

# 20. Operational Rules

Mandatory rules:

* Services dispatch events only after successful persistence.
* Listeners remain focused on a single concern.
* Jobs are independently executable.
* Background work must not block API responses.
* Business logic remains in services.
* Events describe facts, not commands.
* External integrations occur through jobs or listeners, never directly in controllers.

### Recommended architectural enhancement

Before we begin implementation in Milestone 02, I recommend adding an **Outbox Pattern** to the architecture. Rather than dispatching events directly from services, services would persist domain events to an `outbox_events` table within the same database transaction. A background processor would then publish those events to Laravel's event dispatcher.

This pattern guarantees that events cannot be lost if an application crash occurs immediately after a successful transaction but before event dispatch. It also provides a durable audit trail of unpublished events and lays a strong foundation for future microservices or message brokers. While it adds a small amount of infrastructure, it significantly improves reliability and aligns well with the production-grade goals we've established.
